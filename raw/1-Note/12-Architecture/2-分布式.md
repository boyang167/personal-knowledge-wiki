## 事务与隔离级别

在数据库操作中，为有效保证并发读写的正确性，引入**事务隔离级别**；数据库锁用于实现这些隔离级别。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交（Read uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read committed） | 不可能 | 可能 | 可能 |
| 可重复读（Repeatable read） | 不可能 | 不可能 | 可能 |
| 可串行化（Serializable） | 不可能 | 不可能 | 不可能 |

## 分布式事务

**典型场景**：回调支付（订单、库存、支付等多服务）如何保证数据一致。

### ACID 与本地事务

数据库将一次事务中的操作纳入**不可分割的执行单元**：全部成功或全部回滚。

| 属性 | 含义 |
| --- | --- |
| **A** Atomicity | 原子性：全部执行或全部不执行 |
| **C** Consistency | 一致性 |
| **I** Isolation | 隔离性（常配合**锁**） |
| **D** Durability | 持久性（常配合**日志**；log 优先于 data，可恢复） |

**本地事务**：同一数据库、同一服务器。

```text
-- 本地
BEGIN TRANSACTION;
  -- 1. 张三减金额
  -- 2. 李四加金额
COMMIT;  -- 或 ROLLBACK

-- 分布式环境下（伪代码）
BEGIN TRANSACTION;
  -- 1. 本地库：张三减金额
  -- 2. 远程调用：李四加金额
COMMIT;  -- 跨库/跨服务时本地 COMMIT 无法保证全局一致 → 需分布式事务方案
```

**常见产生场景**：

1. 跨数据库实例
2. 多服务访问同一数据库实例（仍可能因多库表/分库而需协调）

### CAP 定理

![image-20231017223858429](../img/image-20231017223858429-1716731158478.png)

**主从同步示例流程**：

1. 商品服务写主库
2. 主库返回成功
3. 商品服务从从库读（可能存在延迟）

**C（Consistency）一致性**：写主库后需同步从库；同步期间可锁从库，避免读到旧数据。

一致性程度：**强一致**、**弱一致**、**最终一致**。

分布式下一致性的代价：写延迟、临时锁、同步失败应报错而非返回旧数据。

**A（Availability）可用性**：请求有响应，不超时、不错误。

**P（Partition tolerance）分区容忍**：

```text
1. 主从同步失败时仍可读写（视设计而定）
2. 单节点故障不影响其他节点对外服务
```

| 组合 | 取舍 | 说明 |
| --- | --- | --- |
| **AP** | 放弃强一致，保分区与可用 | 可接受短暂不一致；订单退款 T+1 到账等；扩展为 **BASE** |
| **CP** | 放弃可用，保一致与分区 | ZooKeeper、跨行转账等 |
| **CA** | 放弃分区 | 非典型分布式；单机关系库 |

<img src="../img/image-20231023210714757.png" alt="image-20231023210714757" style="zoom:50%;" />

分布式系统中 **P 通常不能放弃**，多在 **C 与 A** 之间权衡。

### BASE 理论

**BASE**：Basically Available、Soft state、Eventually consistent。在 CAP 的 AP 方向上扩展，允许短暂不一致，最终一致；对应**柔性事务**。

- **基本可用**：故障时核心功能仍可用（如支付失败仍可浏览商品）
- **软状态**：允许中间态（「支付中」「同步中」）
- **最终一致**：延迟后达到一致（支付成功/失败）

### 方案概览：XA / 2PC / 3PC

#### XA 与 DTP 角色

- **Application Program**：使用分布式事务的应用（勿与 CAP 的 AP 混淆）
- **RM**（Resource Manager）：资源管理器，通常对应数据库实例与分支事务
- **TM**（Transaction Manager）：事务管理器，协调全局事务

<img src="../img/image-20231019205309413.png" alt="image-20231019205309413" style="zoom:25%;" />

**DTP**：TM 与 RM 间接口规范 **XA**；基于 XA 的 2PC 也称 **XA 方案**。

![image-20231018195824121](../img/image-20231018195824121-1716731158479.png)

相关协议：**2PC**、**3PC**。

#### 2PC（两阶段提交）

- **Prepare**：准备阶段
- **Commit**：提交阶段

<img src="../img/image-20231018195551754.png" alt="image-20231018195551754" style="zoom:50%;" />

<img src="../img/image-20231019205533420.png" alt="image-20231019205533420" style="zoom:50%;" />

#### 3PC

（三阶段提交；在 2PC 基础上增加超时与预提交等，降低阻塞风险——细节见专题笔记。）

#### TCC

**Try / Confirm / Cancel**：每个分支实现尝试、确认、取消。

#### Seata

![image-20231018195919596](../img/image-20231018195919596-1716731158479.png)

- **TC**（Transaction Coordinator）：独立部署，维护全局事务状态，驱动提交/回滚
- **TM**（Transaction Manager）：嵌入应用，开启全局事务并向 TC 发起提交/回滚
- **RM**（Resource Manager）：分支事务注册、上报，执行本地提交/回滚

### 最终一致：可靠消息与最大努力通知

**可靠消息最终一致性**、**最大努力通知**：

1. 重复通知
2. 消息校对

### ZooKeeper

**顺序临时节点**：会话结束自动删除，适合锁语义。

### 小结：何时用、用什么

**适用场景**：

1. 集群部署，Java 锁无法互斥
2. 操作共享资源（如唯一用户记录）
3. 多进程同步访问同一资源

**方案对照**：

1. **Redis**：`SET NX EX`、**Redisson**（watchdog）
2. **ZooKeeper**：顺序临时节点
3. **MySQL**：唯一键 / 唯一索引

### 分布式 ID 要求

- 全局唯一
- 高性能、高可用
- 易用、趋势递增（常见业务偏好）

**常见方案**：

| 方案 | 要点 |
| --- | --- |
| UUID | 简单，无序 |
| 数据库自增 / 集群 / **号段** | 依赖 DB，号段减少 DB 压力 |
| Redis `INCR` | 快速，需高可用 Redis |
| **Snowflake（雪花）** | 时间 + 机器 + 序列 |
